# Witnessed hourly upkeep catch-up

Unpaid rent causes property lockout and ordinary-item storage through the existing hourly engine. Catch-up does not evict an owner or return a house. Personal inactivity disposition remains a separate reviewed ninety-day policy; a rent balance or missed hourly charge does not substitute for inactivity evidence.

The existing default refuses an assessment one hour or more overdue. The optional `2026_10_18_housing_witnessed_upkeep_catchup.sql` migration creates empty policy, checkpoint and audit tables. It enables no existing property and invents no historical state. A review must identify the exact estate generation, native plot, current owner kind/ID, catalogue revision, SHA-256 of the complete definitions/cost payload and regions payload, a bounded maximum overdue horizon from1 to2160hours, and a nonempty review reference. Changing that review changes the policy identity.

An enabled, matching review permits a successful **on-time** assessment to write a prospective checkpoint in that same transaction. The checkpoint starts at the next hourly due date, observed before that date. Its contract revision, escrow balance and obligation fingerprint are bound to the actual assessment receipt and advanced contract. Neither policy installation nor an overdue attempt creates a baseline. There is no retrospective reset or supplied-past-snapshot API.

When an hour is overdue, current validated obligations must exactly match that prior checkpoint. The fingerprint binds selected component revision, all currently billable placed items, custody bytes, storage revisions, creator/component IDs, delinquency markers, house/interior scope and content proofs. The policy binds the complete catalogue/costs and region hashes. The exact escrow balance and append-only escrow receipt count are checked; a later deposit cannot fund an unknown earlier hour, and a deposit/withdraw roundtrip cannot conceal intervening changes. Placement-history count, high-water ID and state summary also prevent a new/removed placement from disappearing into an apparently unchanged current scene. Historical evidence must be preserved; direct SQL edits, pruning, or unjournaled content/price modifications are outside this authority and require separate evidence recovery, never silently accepted as known history.

Each accepted catch-up call runs the existing full transaction for **one** due hour: actual escrow charge, immutable per-hour/property/item/scope receipts, normal stow/expiry behavior, due advancement and checkpoint advancement. System-generated stow/expiry transitions become the next checkpoint only in that same transaction. Unknown or partially affordable cohorts and alternate currencies retain their existing refusal. Historical hours use their own UTC rounding phase. A failed late checkpoint write rolls back currency, receipts and the due clock together. Receipt replay never charges twice, including after uncertain COMMIT.

`ProcessDue` retains its fair100-property keyset bound and dispatches no more than one due hour per selected property in a pass. It does not loop over an entire backlog or let an unsupported old property suppress later dispatch. The original pre-gap anchor and observation are retained across catch-up, with a fixed reviewed horizon; processing does not extend its own historical authority.

Ordinary changes while billing is current can be observed by the next genuine on-time assessment, which establishes a new prospective checkpoint. A change after a missed hour blocks catch-up because its timing is unknown. If the already overdue history cannot be proved, the server leaves it unsupported; it does not reset the clock to manufacture a clean baseline. A later on-time observation can renew authority only when existing due progression has actually reached that current hour through valid receipts. This feature deliberately does not recover arbitrary pre-installation arrears, mixed funding timelines, changed furnishings, or lost catalogue history.

Private validation covers actual SQL assessments/replay, no-review/no-baseline refusal, catalogue/selection/balance/receipt-history guards, closed-placement history, a fixed horizon, post-debit failure rollback, one-hour dispatch, prospective reanchoring and insolvency retaining ownership. It is not a new native full-furnished-house or crash-execution claim. Default behavior is unchanged when this optional review is absent.

For future paid acquisitions, the optional migration also adds `max_catchup_hours` to the existing catalogue-bound enrollment policy. Its default is zero; older schemas also read as zero. An explicit1..2160 value makes the existing authenticated purchase transaction insert an exact new-generation catch-up review together with acquisition, debit and rent enrollment. It revalidates actual catalogue hashes and the current enrollment row. A failure rolls back the acquisition; no checkpoint or past assessment is manufactured at purchase. Existing properties and policy rows are not automatically changed.
