# Guild inactivity and safe dissolution

The original RoF2 management window states that a guild plot is released if no guild member has logged in for30 days. This implementation is explicitly opt-in. It does not infer automatic eviction from an unpaid rent cycle, and it does not copy the modern non-member neighborhood eviction setting into the2013 protocol.

Apply `2026_10_18_housing_guild_inactivity_returns.sql` after the personal offline delivery, packing, creation and typed-origin migrations. No existing estate is enrolled. The guild-specific policy pins the ownership generation, native plot, catalogue revision, exact definition/region hashes, recipient and2592000-second interval. The recipient must still be the current guild leader and a real member at execution. Reuse the exact per-estate delivery review, and separately opt into packing and creation when needed. These are explicit local recipient/refund/capacity choices, not recovered original guild-wide distribution rules.

One bounded fair worker visits at most100 reviewed guild estates per pass. It locks the real guild identity before locking/revalidating ownership. It then locks the current roster and character rows, takes the most recent current-member last_login, and refuses recent, unknown/deleted or actively session-reserved members. This is a current-roster activity policy: it does not reconstruct departed-member historical activity. Enabled housing inventory session enforcement must cover participating zones. Existing pending item/coin/house applications and occupied house interiors prevent disposition.

Supported returns reuse the same complete transaction and custody validation as personal inactivity. An empty plot refunds unused escrow; a supported single small crate can preserve ordinary yard items and one furnished registered guild hall, including its permanent interior and closet. A separate review can create that crate when absent. Every root, hall and room item must belong to the explicit recipient; mixed contributors, vault contents, evolving items, unsupported models, insufficient crate capacity or saved-inventory space defer the whole operation. No partial return or guild-bank withdrawal occurs. The original purchase price is not refunded.

Guild disposition uses separate immutable retirement, delivery, packing and creation receipts. Inventory, money, crate membership, ownership release and receipts commit together. Typed crate creation origin3 records the recipient permanently; a later leader change never changes the creator of delivered cargo. New acquisition of the plot has a distinct ownership generation and cannot replay an old return.

Guild dissolution now locks the same guild row as acquisitions and refuses active housing, unresolved escrow, custody, bindings or applications. Checked dependent deletion commits before local guild cache removal. SQL errors and uncertain commit results retain the cache. Raw guild estate provisioning also requires the locked guild identity. Safely delivered historical occupied cargo currently remains a conservative dissolution blocker until a separate settlement proof is available; it is never discarded merely to complete disbanding.

No client opcode or wire-layout change is needed. Native acceptance, private SQL verification and limitations are recorded in the batch report; implementation alone does not certify every hall or multi-contributor return.


The later `offline_return_batches.md` extension supports reviewed mixed-recipient/vault/multiple-bin disposition and a complete immutable settlement proof. Its validated new returns can pass the dissolution interlock despite safely retained historical crate cargo. The earlier blanket historical-cargo refusal above still applies when that proof is absent or invalid.
